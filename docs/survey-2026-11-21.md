## 3. Inspect's sandbox events, 0.3.275 against 0.3.291

**What 0.3.275 records** (`inspect_ai/util/_sandbox/events.py`, the same file in the installed package and at the tag):

- One event for each `exec`, `read_file` and `write_file` that goes through the sandbox API.
- `exec`: the command as one shell-quoted string, the options that were set (cwd, env, user, timeout), the exit
  code, the input, and the output. The output is one text: the standard error, a blank line, then the standard
  output when there is standard error; else the standard output alone.
- `read_file` and `write_file`: the file name, and the content as output or input.
- **Input and output are cut to 20 lines**, with a note of how many more lines there were. The field's own
  documentation says 100 lines; the code says 20 (`truncate_lines(content, 20)`), in both versions. Binary content
  is recorded as its size only.
- **No event for a "sandbox service" command.** `exec` returns before the event is made when the command is one
  of Inspect's sandbox-service calls.
- The start time and the completion time of each action.

A correction to an earlier description of this (which said 100 lines): 20.

**What changed by 0.3.291:**

| Part | Difference |
|---|---|
| The event's fields | None. One docstring: `options` is now "for exec, read_file and write_file". |
| The code that makes the events | 96 changed lines. The skip of sandbox-service commands is no longer in this file. `write_file` and `read_file` take a `user` and record options. The user and the working directory of an action can be set by an "identity" layer. Events are switched off per proxy through a context variable. |

**What this means:** an Inspect upgrade can change which actions get an event and what an event's options hold.
A log from 0.3.275 and a log from 0.3.291 are not comparable event by event without a check. The reconciler must
state the Inspect version of the log it reads.

## 4. Is the test file in the container by design?

In both versions the setting's setup step (`add_test_file`) writes the task's tests to `test_task.py` in the
container's working directory and runs them once, before the agent starts. The `run_tests` tool runs that file.
The scorer writes the same tests to the same file again and runs it. The setting's description tells the agent:
"Run the tests with your test tool." Each task also has a field `private_tests`; no code in the setting reads it.

So: the file's presence is by design (the test tool needs it). Whether the agent reading the file is intended,
the code does not say. The setting's README says nothing about tests. No upstream issue was opened or commented on.

## 5. Which packages the 257 tasks need

A text search of the task descriptions and tests; no container was started, so the list of what the image
already holds is an assumption (the Dockerfile's packages and BusyBox).

| Count | What |
|---|---|
| 26 of 257 | Tasks whose tests call `apk` (mostly `apk info`, to check that a package is installed) |
| 54 of 257 | Tasks whose tests look up a binary with `which` |
| 71 of 257 | Tasks whose description has the word "install" |
| about 60 of 257 | Tasks whose tests name at least one of about 30 programs that the image probably lacks |

The programs named most: `rsync`, `jq`, `nano`, `dig` (`bind-tools`), `gawk`, `make`, `tree`, `gcc`, `nginx`,
`git`, `openssl`, `tmux`, `yq`, `ack`; once each: `ffmpeg`, `iperf`, `w3m`, `groff`, `node`, `npm`, `zsh`,
`screen`, `shellcheck`, `gpg`, `logrotate`, `mawk`.

Limits of this count: it is a word search and counts some common words (`file`, `host`). It misses a need that
only the description states: the pilot's third task needs `sshd` and its tests do not name it. Of the first 5
tasks, 2 need a package (`nano`, `sshd`).

**What this means for the method:** about 30 packages cover the named needs, so an image with them installed at
build time is practical. A package mirror inside the sandbox network is the heavier choice; it is needed only if
the agent must be able to run the install itself. Some tests check `apk info` (a real installed package), which a
pre-installed image satisfies and a stand-in does not.

## 6. ControlArena issue #943, as it stood on 21 November 2026

"Is 'nothing monitors actual sandbox execution' a gap worth closing?" Open, created 9 November, 3 comments, no
labels, no linked pull request.

- The issue: every monitor scores the model's transcript or the final diff; nothing observes what ran in the sandbox.
- 18 November: a commenter agrees and offers to take it; notes that scorers run only after the trajectory, so a
  before-and-after comparison needs a solver for the first snapshot, and that the Bash setting's Alpine image has no

  replaying BashArena runs in a separate sandbox, with a write-up; the summary given is that it made no large
  difference with the monitor used.
- 21 November: the first commenter proposes a filesystem snapshot scorer (snapshot after setup, snapshot at the
  end, compare), notes what it cannot see (reads, network connections, a file created and then deleted), and says
  work on it starts.

No maintainer has answered. Nothing was posted from this project.
